## 工具指南

所有工具必须遵守以下指令。
- `apply_patch`工具在底层使用了命令行调用来实现功能，而windows的命令行输入，最长支持8k字符，所以不要超出这个字符长度限制。
- 当前在 windows 上，所以不要使用 `cat`、 `sed`、 `awk` 之类的 GNU 工具，取而代之的是使用 pwsh 脚本。
- 使用 pwsh 的 `Get-Content` 来读取文件内容，但这个命令默认不会输出行号，所以需要通过管道操作符来添加行号，不要使用 `python` 来读取文件内容。
- call binaries directly in functions.shell, always set workdir, and avoid shell wrappers such as `bash -lc`, `sh -lc`, `zsh -lc`, `cmd /c`, `pwsh.exe -NoLogo -NoProfile -Command`, and `powershell.exe -NoLogo -NoProfile -Command`.

### 多智能体相关

如果存在`spawn_agent`工具。
- 子智能体使用配置的 reasoning，不要自作主张修改。

## 表达习惯

- 禁止任何的阿谀奉承，需要精准指出用户的错误，并一刀见血的给出锋利的建议。

## 编码原则

### 单一数据源（SSOT）

- 分层数据流对象可以单向标注彼此间的关联，从而更好地进行数据源追溯。
- 每一层数据都可以有自己的局部数据拓扑表达，但他的上游源头则永远是单一的，计算函数是清晰的。
- 在少数情况下，可能某个上层对象需要和某个底层对象做 hashmap 式映射，而不是纯粹的显式单射或者显式Nv1映射。这种情况尽量不要发生，因为有性能问题。但如果在反复分析后，基于缓存性能等实在无法避免的原因，必须要这么做，则需要和用户提前沟通，征得用户的同意后，落盘文档特殊说明。再次强调，这不应该是系统设计时候的常态，宁愿把映射关系移动到最顶层由用户来显式关联，多创造一个顶层对象，也要禁止随意的底层 hashmap 式隐式映射底层对象管理。

### 单向数据流（UDF）

- 永远让内存（即数据）顺着一个方向流动，比如最终走向 GPU（VB IB UBO GPU 其他状态）或者从数据库走向 socket 网络流量。

### 快速路径（FastPath）

- 在多层数据的转换计算过程中，除了对数据流的整体转换，也允许设计快速路径，对局部数据进行脏标志和增量计算转换。
- 比如骨架屏填充模式：先把系统快速简单走完闭环，在异步加载这样的异步事件后，再针对个别内存点进行最终值替换。

### 把数据源的生命周期管理交给用户

- 数据源的生命周期管理，需要交给用户，而不是在内部默默管理，一般就是最顶层的 main 函数代码，这样下面每一层只需要负责维护单向数据流带来的中间对象的拓扑关系，而他们的生命周期普遍和数据源保持同步。
- 如果出现了 hashmap 式生命周期管理，可以使用引用计数、垃圾回收（GC）或者手工特殊处理。

### 最小化内存拷贝和流式计算

- 在数据流动的计算过程中，因为内存拷贝和堆对象申请的性能代价是巨大的，所以要最小化内存拷贝和堆内存分配。
- 考虑到原地计算转换的难度，有时候要设计成流式转换系统，并精准的设计 DFS 和 BFS 流式转换框架，提前和用户确认好设计思路。

## 测试

## 重构

### 基于绞杀思路的重构

- 当用户要求重构代码的时候，先把重构后的最外侧边缘形状和用户讨论清楚，确保完美符合用户预期，之后再向内逐步绞杀。

### 复杂问题要通过反思忘记现有代码事实寻找最优解

- 不要总是以既定代码作为基础假设，陷入局部最优的思考：要从第一性原理出发，寻找逻辑的起点后，再从最底层的 api（比如 webgpu） 和最终达成目的开始思考，以终为始，砍掉现有的中间冗余计算过程，基于全链路思考最优计算路径。

### 零遗留代码残留

- 不需要为兼容面、历史遗留等问题保留遗留代码，当前只需要保证最终代码足够的简洁、优雅、直白，completion-only，no fallback。
- 不需要为了保证测试用例的完成度，而在重构时强行留下兼容路径，相反，如果测试代码和重构代码冲突，可以直接删除这个测试用例和遗留代码，测试在项目中重要度并不高。
